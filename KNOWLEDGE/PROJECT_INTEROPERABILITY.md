# مشروع التكامل: MAL ↔ ilm-al-kitab ↔ UORI/UORI+

## الغرض

هذا الملف يحدد كيف يستفيد مستودع `ilm-al-kitab` من النجاحات المثبتة في مستودع `arabic-math-lang` دون نسخ أعمى أو تعديل صامت على أساس محمي. يظل `KNOB.md` الذاكرة المركزية، بينما يبقى مستودع اللغة الرياضية المصدر المرجعي الخارجي حتى تُعتمد كل قطعة داخل المستودع الجديد بدليل مستقل.

## قاعدة المصدر

- `arabic-math-lang`: **مرجع MAL الخارجي**، للقراءة والانتقاء والمقارنة.
- `ilm-al-kitab/MAL`: **مساحة التكامل الداخلية**، ولا تُرفع إليها ملفات إلا بعد تحديد المصدر والبصمة والاختبار.
- `UORI` و`UORI_PLUS`: **طبقات تصميم وتكامل**؛ لا تُعلن منفذة ما لم توجد ملفات واختبارات وأدلة.
- `evidence/`: المخرجات الخام والبصمات.
- `KNOB.md`: سجل الحالة والقرارات والحدود، وليس بديلاً عن الدليل الخام.

## ما ثبت في MAL داخل ilm-al-kitab

وفق سجل Git الحالي، توجد نقاط تحقق للمكوّنات الآتية:

| المكوّن | المرجع | الحالة الحالية |
|---|---|---|
| Lexer حتمي | `7f8760f` | `PROVEN_FOR_SCOPE` بحسب سجل المهمة؛ يجب إعادة الاختبار عند تغيير البيئة |
| Parser أساسي | `fdd3ba2` | مسجل مع دليل 9 اختبارات |
| دعم λ في مسار Python/AOT | `585cad6` | `PROVEN_FOR_SCOPE` بحسب السجل؛ لا يُعاد فتح `math_complete.py` دون فشل مثبت |
| Arena NodeID و10K | `fbf4dab` | مسجل كـ `STAGE0_GATE=PASSED` مع أدلة |
| Parser λ الحالي | `ea7979d` | يجب إعادة التحقق محلياً قبل اعتماد أي claim جديد |

هذه الحالات لا تعني صحة عامة لكل MAL؛ بل تثبت النطاق المسجل فقط.

## قاعدة التلاقح

1. اقرأ `KNOB.md` و`docs/CONSTITUTION.md` قبل أي تغيير.
2. افحص سجل Git والأدلة قبل إعادة تنفيذ مهمة قد تكون مثبتة.
3. انقل المفهوم لا الملف، إلا إذا كانت المطابقة والملكية والرخصة والنطاق واضحة.
4. استخدم واجهة صغيرة بين الطبقات: AST/NodeID/diagnostics/evidence، لا اعتماداً على تفاصيل داخلية غير مثبتة.
5. كل ترقية من `RESEARCH` أو `PLANNED` أو `ABSTAIN` إلى `PROVEN_FOR_SCOPE` تحتاج مخرجاً خاماً، SHA-256، اختباراً مستقلاً، ونطاقاً محدداً.
6. فشل واحد يبقي المهمة `FAILED` أو `ABSTAIN`، ولا يسمح بتسجيل `PROVEN`.

## مراحل التكامل

### المرحلة A — جرد للقراءة فقط

تُسجل أسماء الملفات، commit المصدر، البصمات، الاختبارات، والرخصة. لا نسخ ولا submodule قبل اكتمال الجرد.

### المرحلة B — عقد واجهة

يُكتب عقد صغير يحدد تمثيل `NodeID`, AST, errors, diagnostics، وما إذا كان المسار حتمياً أو يسمح بالشبكة. العقد نفسه `PLANNED` حتى يختبر.

### المرحلة C — تكامل انتقائي

تُنسخ فقط الملفات اللازمة إلى `MAL/src` أو تُربط بمرجع ثابت. يجب أن يكون كل ملف مصحوباً بمصدر وcommit واختبار.

### المرحلة D — تحقق تفاضلي

تشغّل اختبارات MAL الأصلية واختبارات التكامل الجديدة، وتقارن stdout والبصمات. لا يُعتمد التكامل إذا تغير baseline بلا تفسير.

### المرحلة E — توجيه LLM

يقرأ النموذج هذا الملف و`KNOB.md` أولاً، ثم يقرأ أقل مجموعة ملفات تكفي للمهمة، ويقدم خطة وكوداً منفصلين. النموذج لا يقرر الحالة الدستورية ولا يكتب `PROVEN` من تلقاء نفسه.

## سياسة الوصول إلى Git

المستودع العام يمكن لأي نموذج أو آلة قراءته عبر HTTPS، لكن الكتابة تحتاج صلاحية. لا توضع مفاتيح أو PAT داخل remote أو prompt. يستخدم الـVPS alias `github-kitab` مع مفتاح مخصص، وقد تم تنظيف remote مستودع `arabic-math-lang` من رمز وصول كان مكشوفاً.

## الحالات الحالية غير المثبتة

- لا توجد أدلة كافية هنا لإعلان UORI أو UORI+ منفذين.
- لا يُفترض أن كل نجاحات `arabic-math-lang` قابلة للنقل إلى MAL الداخلي.
- فشل `cargo` في جلسة الفحص الحالية لأن `cargo` غير موجود في PATH؛ لا يُسجل هذا كفشل للمصدر، بل كـ `ENVIRONMENT_BLOCKED`.
- يجب مراجعة أي evidence hash فاشل قبل إعادة استخدامه؛ أحد ملفات Parser القديمة لا يطابق الملف الحالي.
